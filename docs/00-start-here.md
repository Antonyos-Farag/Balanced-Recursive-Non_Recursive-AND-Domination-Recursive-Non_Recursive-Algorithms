# 00 -- Start here

This chapter is the map: what the repository contains, what each chapter is for,
and which command prints the evidence behind a claim you are about to read.

## The shortest possible summary

Four programs were submitted for one assignment:

* balanced substrings, solved with a double loop;
* balanced substrings, solved with recursion (`TryStart` / `TryEnd`);
* a dominator (majority element), solved with a Boyer-Moore vote;
* a dominator, solved by divide & conquer.

They are archived here exactly as submitted. Around them, this repository adds a
repaired and extended implementation of each algorithm, a test suite that checks
every claim, a tracing layer that prints what the code actually does, benchmarks
with real numbers, and these chapters.

The result of the review, in four lines:

| program | verdict | what to do about it |
|---|---|---|
| balanced, loop | **wrong** (silently, on ordinary input) | move one line inside the loop |
| balanced, recursion | correct, but crashes on non-ASCII and long input | check ASCII, respect the stack |
| dominator, loop | correct; contract differs from its sibling | agree on one "no answer" value |
| dominator, recursion | correct for ordinary arrays; mishandles `None` | use a result object, not a sentinel |

## What is where, and why

```
algorithms/
  original/            the four submissions, frozen; adapters.py wraps them
  balanced/            the problem solved eight ways (oracle, loop x2, round trip,
                       recursion x2, pair scan x2)
  dominator/           the problem solved four ways, on one result type
  tracing.py           turns internal state into ASCII you can read
  support.py           instrumentation: read counters, deep recursion, timing

docs/                  chapters 00-07, plus traces/ (real program output)
docs/traces/           generated by tools/make_traces.py, checked by tests
tests/                 190 tests; one class per claim in these chapters
tools/                 demo, bench, make_traces, freeze_archive, run_all,
                       check_playground, serve_playground
playground/index.html  the same algorithms, animated, in one file
```

Three conventions are worth knowing before you read any code:

1. **The archive never changes.** `algorithms/original/` is evidence. Its digests
   are recorded and checked, so a chapter's bug list cannot drift away from the
   code it describes.
2. **The library speaks one contract per problem.** Balanced functions return
   `(length, sorted_list_of_substrings)`; dominator functions return a
   `Dominator` or `None`. The archived programs speak three other dialects, so
   `algorithms/original/adapters.py` translates them -- output shape only, never
   behaviour.
3. **Input is validated, not guessed.** Non-letter characters raise `ValueError`
   rather than being skipped (the two submissions disagree with each other on
   this; the repository picks one policy and applies it everywhere, and the
   difference is documented instead of hidden).

## Five commands

```console
# 1. the guided tour: two tables, one bug, one crash, one sentinel
python -m tools.demo

# 2. everything: 190 tests, trace freshness, archive digests, then the tour
python -m tools.run_all

# 3. the numbers behind chapter 05
python -m tools.bench --sizes 125,250,500,1000

# 4. regenerate the output quoted in the chapters
python -m tools.make_traces

# 5. the algorithms in a browser
python -m tools.serve_playground                    # then open localhost:8000
#   (python -m http.server 8000 --directory playground also works; the tool
#    above adds HTTP/1.1 keep-alive, charset=utf-8, a bigger listen backlog
#    and Cache-Control: no-store, which matter behind a proxy or an iframe)

# 6. check that page against the Python code (needs node; skipped without it)
python -m tools.check_playground
```

No installation, no dependencies, no virtual environment: everything runs on a
plain CPython 3.8+ with the standard library.

## How to read the trace files

`docs/traces/*.txt` are raw program output with a header explaining how to
regenerate them. They are the primary sources for the chapters: when a chapter
shows a tree or a table, that table exists as a file, and
`tests/test_docs_traces.py` fails if the file and the code disagree.

The one exception is `bench.txt`, which contains timings: those depend on the
machine, so it is regenerated but not drift-checked.

## A note on what "educational" means here

It does not mean "simplified to the point of being wrong". The code in
`algorithms/` is production-shaped: type hints, docstrings whose examples are
executed by the suite (`tests/test_doctests.py`), no shortcuts that the
documentation then has to apologise for. Where a trade-off was made, it is written down in the code and in
`docs/05` rather than hidden. Two examples:

* `pair_scan` is `O(26^2 * n log n)`, not an asymptotically linear algorithm,
  because the only linear-time constructions we could find solve the problem for
  two or three distinct characters, and lifting that to the whole alphabet is a
  research question rather than a paragraph. `docs/01` §7 says exactly what is
  and is not being claimed.
* `ReadCounter` splits its counts into "positions examined" and "characters
  copied", because conflating them produced a misleading table the first time
  this repository tried to measure the pair scan.

The exercises in `docs/07` are the other half of that: they are the questions
this repository could not answer in the space it has.
